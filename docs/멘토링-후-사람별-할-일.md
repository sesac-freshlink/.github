## 김진아

### 배포 알림 웹훅
- [ ] 디스코드(또는 슬랙) 채널에 웹훅 URL을 만들고, 조직 비밀(Organization secret)로 넣는다. 예: `DEPLOY_WEBHOOK_URL`.
- [ ] 서비스 5개가 같이 쓰는 재사용 워크플로 `.github/.github/workflows/spring-build.yml`의 `build`(dev 배포)·`promote`(prod 승격) 작업 끝에 알림 단계를 넣는다. `if: always()`로 성공·실패 둘 다 보낸다. 이 파일 하나만 고치면 서비스 5개에 모두 적용된다.
- [ ] 메시지에 서비스 이름, 환경(dev/prod), 결과, 커밋 7자리, 실행 링크(`github.server_url/…/actions/runs/run_id`)를 넣는다.
- [ ] 프론트 배포 워크플로(frontend `frontend-deploy`)에도 같은 알림 단계를 넣는다. 프론트는 공통 워크플로를 안 쓰므로 따로 고친다.
- [ ] 서비스 레포 `ci.yml`이 새 비밀을 넘기도록(`secrets: inherit` 또는 명시) 확인한다.
- [ ] (선택) ArgoCD 동기화 실패도 알리려면 ArgoCD Notifications에 같은 웹훅을 연결한다. 이미지 올리기는 성공했는데 파드가 안 뜨는 경우를 잡는다.

### 배포 대응 문서 (주도)
- [ ] 배포 실패 알림이 오면 누가 보는지 정한다. 기본은 그 서비스 담당자, 인프라 원인(ECR·OIDC·gitops 커밋 실패)은 김진아.
- [ ] 되돌리는 순서를 적는다. ① gitops `envs/<환경>/<서비스>/values.yaml`의 `image.tag`를 이전 7자리로 되돌리는 커밋 → ② ArgoCD가 다시 맞추는지 확인 → ③ 원인 고친 PR을 다시 올린다.
- [ ] prod는 release PR을 "Create a merge commit"으로 합쳐야 승격된다는 점, Squash로 합쳤을 때 "ECR에 없다"로 멈추는 경우의 대처(infra README 4-13)를 문서에 연결한다.
- [ ] 서비스별로 "실패했을 때 내가 볼 곳"(Actions 로그, ArgoCD 화면, Grafana/Loki 로그) 칸을 만들어 두고, 태우님·경우님이 자기 서비스 칸을 채우게 한다.

### 실시간 매출 SSE 길 열기 (경우님과)
- [ ] gateway가 SSE 응답을 끊거나 모아서 보내지 않게 한다. 해당 경로에 응답 타임아웃을 늘리고 버퍼링을 끈다.
- [ ] ALB 유휴 타임아웃(기본 60초)이 연결을 끊지 않도록 늘리거나, 서버가 주기적으로 빈 이벤트(heartbeat)를 보내게 경우님과 정한다.
- [ ] 파드가 2개 이상이면 연결된 파드에만 이벤트가 가므로, 매출 이벤트를 모든 파드가 받는 방법(예: SNS 팬아웃, 파드 1개로 시작)을 경우님과 정한다.

### 재시도·DLQ 공통
- [ ] SQS DLQ에 메시지가 쌓이면(`ApproximateNumberOfMessagesVisible > 0`) CloudWatch 알람 → 위 웹훅 채널로 알린다.
- [ ] DLQ 메시지를 원래 큐로 되돌리는 방법(SQS 콘솔 "DLQ redrive" 또는 `aws sqs start-message-move-task`)을 문서로 남겨 팀원이 직접 재처리하게 한다.

### 리프레시 토큰 설정 (경우님과)
- [ ] 지금 값은 ID 토큰 1시간, 리프레시 1일(infra `modules/cognito` `id_token_validity_hours`, `refresh_token_validity_days`). 필요하면 dev·prod 값을 정해 바꾼다.
- [ ] Amplify vs BFF 저장 위치 이유는 `docs/기술스택과 선택이유.md` 3-7에 있으니 멘토 질문이 오면 이 문서로 답한다.

### 구글 로그인 Cognito 설정 (경우님과)
- [ ] Google Cloud 콘솔에서 OAuth 클라이언트를 만들고, 승인된 리디렉션 URI에 Cognito 도메인 `/oauth2/idpresponse`를 넣는다.
- [ ] infra Cognito 모듈에 Google IdP(`aws_cognito_identity_provider`)와 속성 매핑(email, name)을 추가하고 앱 클라이언트의 지원 IdP에 Google을 넣는다. 콜백·로그아웃 URL에 dev·prod 프론트 주소를 넣는다.
- [ ] 클라이언트 비밀은 Terraform 코드에 쓰지 않고 SSM/Secrets Manager에서 읽는다.
- [ ] 구글로 처음 가입한 사람도 post-confirmation Lambda가 CUSTOMER 그룹에 넣는지 확인한다(구글 가입은 트리거 출처가 `PostConfirmation_ConfirmSignUp`이 아닐 수 있다).

### 점포 이미지·지도 키 (경우님과)
- [ ] 점포 이미지용 S3 버킷(또는 기존 프론트 버킷의 경로)과 업로드 방식(서버가 발급하는 presigned URL)을 정하고 IRSA 권한을 member-service에 준다.
- [ ] 지도 API 키를 보관할 곳(프론트 빌드 변수 vs SSM)을 정한다. 프론트에서 쓰는 키면 도메인 제한을 건다.

### 인증서
- [ ] 지금도 CloudFront 기본 주소로 HTTPS가 된다(기획안 214줄). 멘토 의도가 "자체 도메인 + 인증서"인지 먼저 확인한다(의도는 추정).
- [ ] 자체 도메인을 붙인다면 Route 53 호스팅 영역, `us-east-1` ACM 인증서(CloudFront용)와 `ap-northeast-2` ACM 인증서(ALB용), DNS 검증 레코드, CloudFront·ALB 연결을 infra에 추가한다. 도메인 비용을 예산에 반영한다.

### 대형 테스트 인프라 (전원 일 중 내 몫)
- [ ] 테스트 중 Grafana에서 서비스별 응답 시간, 오류율, 파드 CPU·메모리, 노드 여유, RDS 연결 수·CPU, SQS 대기 메시지 수를 본다. 이 화면을 대시보드 하나로 묶는다.
- [ ] 테스트 전에 노드 그룹·RDS가 켜져 있는 시간인지(on/off 일정) 확인하고, 필요하면 노드 수를 잠시 늘린다.

## 이태우

### 재고 복원 (경우님 환불과)
- [ ] 결제 후 취소·환불(경우님 A9·A10) 때 order가 보내는 "재고 복원" 명령을 inventory가 받아 lot 수량을 되돌린다. 메시지 이름·필드는 경우님과 정한다.
- [ ] 같은 명령이 두 번 와도 한 번만 복원되게 멱등 처리한다(common v0.2.0 멱등 키 사용).
- [ ] 이미 유통기한이 지난 lot이면 복원할지(판매 불가로 남길지) 정한다.

### 재시도·DLQ (inventory)
- [ ] 재고 명령 큐의 DLQ로 간 메시지를 다시 처리하는 방법을 정한다. 김진아가 만드는 공통 재처리(redrive) 절차를 쓰고, 다시 넣어도 멱등이라 중복 차감이 없는지 확인한다.
- [ ] DLQ로 가는 조건(최대 수신 횟수)과 그때 남기는 로그(주문 번호, 이유)를 확인한다.

### 알림 이벤트 (알림 서비스를 만들기로 하면)
- [ ] 재고 부족(임계치 아래)과 유통기한 임박 이벤트를 inventory에서 Outbox로 발행한다.

### 재고 검색 필터
- [ ] 점주 재고 화면에 상품명 검색, 임박만, 품절만 필터를 넣는다.
- [ ] 재고 목록 API에 `q`(상품명), `status`(임박·품절 등) 조건을 추가한다. 페이지 나누기와 같이 쓴다.

### 물품 검색 (고객)
- [ ] 고객 상품 목록(U-10)에 상품명 검색을 넣는다. 고객 목록은 들어올 때·새로 고칠 때만 불러오는 지금 방식을 유지한다.

### 상품 상세 (고객)
- [ ] 고객 상품 상세 화면(가격, 남은 수량, 유통기한, 점포)과 상세 API를 만든다.
- [ ] 상세에서 주문 화면(경우님)으로 넘어가는 연결을 경우님과 맞춘다.

### 유통기한 달력
- [ ] 점주 화면에 lot 유통기한을 달력으로 보여 준다. 날짜를 누르면 그날 끝나는 lot 목록을 보여 준다.
- [ ] 기간(월)별 lot 조회 API를 추가한다.

### 대형 테스트 (전원 일 중 내 몫)

## 같이 정할 일

담당이 아직 정해지지 않았거나 세 사람이 모두 걸친 일이다. 정해지면 위 각자 목록으로 옮긴다.

### 매출 조회 (경우님 제안, 태우님과 협의)
- [ ] 결제 금액은 order에 있으므로 점포별·기간별 매출 API와 점주 매출 화면은 경우님이 맡는 안.
- [ ] 재고 쪽 판매 수량 통계와 겹치는 부분은 태우님과 나눈다.

### 상품별 판매 순위
- [ ] 기준을 정한다. 결제 기준이면 order(경우님), 재고 출고 기준이면 inventory(태우님).

### 선착순 구매(대기열) (경우님·김진아·태우님)
- [ ] 주문 앞에 대기열을 두고 순번이 온 사람만 주문하게 한다. 대기열 API·화면은 경우님, 재고 한도는 태우님.
- [ ] Redis(ElastiCache)는 MVP에서 뺀 것이라(기획안 132줄) 김진아가 비용과 함께 인프라를 추가할지 정한다.

### 알림 서비스 (김진아 제안)
- [ ] notification-service를 새로 만들지 정한다(기획안 129줄). 만들면 서비스 뼈대·배포는 김진아, 주문 알림 이벤트는 경우님, 재고 부족·유통기한 이벤트는 태우님.
- [ ] 알림을 받을 곳(화면 알림, 메일 등)을 정한다.

### 배포 대응 문서 채우기 (전원)
- [ ] 김진아가 만든 배포 대응 문서의 자기 서비스 칸(실패 때 볼 곳, 되돌리는 기준)을 각자 채운다.

### 대형 테스트(100명 구매) (전원)
- [ ] 100명이 동시에 주문·결제하는 시나리오로 응답 시간, 성공·실패 수, 재고 음수 0건, 중복 주문 0건을 보여 준다.
- [ ] 각자 몫은 위 목록에 있다(태우님 동시 예약 스크립트, 경우님 주문·결제 시나리오, 김진아 Grafana 지표와 노드·DB 여유).
