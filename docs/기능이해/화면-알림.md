# 화면 알림 (notification-service, SSE)

> 담당: 김진아 · 갱신: 2026-10-30 · 상태: 현재

점주와 고객 화면 위쪽의 알림 종(🔔)이 어떻게 채워지는지, 그리고 **inventory가 보내야 하는 쪽지 형식**을 적는다. 쪽지 형식을 바꾸면 이 문서, common `NotificationMessage`, notification-service를 같은 날 같이 고친다.

## 1. 알림 종류 (10/30 확정, 이것만 한다)

| 종류 (`kind`) | 받는 사람 | 언제 | 화면 문구 (notification-service가 만든다) | 누르면 |
| --- | --- | --- | --- | --- |
| `EXPIRY_IMMINENT` | 그 점포 점주 | lot이 유통기한 24시간 안으로 들어올 때 (NORMAL → IMMINENT) | **유통기한 임박** · 매운 컵라면 115g 4개의 유통기한이 10월 31일 23:59에 끝나요 | `/owner/expiring` |
| `EXPIRED` | 그 점포 점주 | lot의 유통기한이 지날 때 (→ EXPIRED) | **유통기한 경과** · 매운 컵라면 115g 4개의 유통기한이 지났어요. 폐기해 주세요 | `/owner/expiring` |
| `RESTOCKED` | 그 점포·상품에 재입고 알림을 신청한 고객 | 팔 수 있는 수량이 0이던 상품이 입고로 1개 이상이 될 때 | **재입고 알림** · 매운 컵라면 115g 상품이 다시 들어왔어요 | 그 상품 상세 화면 |

새 주문, 재고 부족, 결제 완료, 픽업, 선착순 차례 도착 알림은 하지 않는다. 그래서 **order-service가 보낼 알림 쪽지는 없다.**

## 2. 흐름

```
inventory-service ──(Outbox, 같은 트랜잭션)──▶ SQS <env>-notification-events ──▶ notification-service
                                                  (3번 실패하면 DLQ → 디스코드 DLQ 채널)        │ 알림 표에 저장
                                                                                               ▼
브라우저 EventSource('/api/notifications/stream') ◀── CloudFront ◀── ALB ◀── gateway ◀── SSE로 바로 밀어 줌
```

1. inventory가 lot 상태를 바꾸거나 입고를 처리하는 **같은 트랜잭션**에서 `OutboxWriter.save`로 쪽지를 남긴다. 쪽지는 common 발행기가 큐로 보낸다.
2. notification-service가 쪽지를 받아 받는 사람을 정하고, 알림 표에 저장한다. 같은 `messageId`는 한 번만 처리한다(common `ProcessedMessages`).
3. 저장이 끝나면(커밋 뒤) 그 사람이 열어 둔 SSE 연결로 바로 보낸다. 화면은 종의 숫자를 올리고 sonner 토스트를 띄운다.
4. 연결이 끊겼다 다시 붙으면 마지막으로 받은 알림 번호(`Last-Event-ID`) 뒤의 알림을 이어서 보낸다(최대 50개).

## 3. 쪽지 형식 (inventory → notification-service)

- 큐: `${QUEUE_PREFIX}notification-events` (표준 큐, FIFO 아님). dev는 `dev-notification-events`, prod는 `prod-notification-events`. 개인 큐를 쓰는 로컬 실행은 `QUEUE_PREFIX`를 따른다.
- 클래스: common **v0.6.0** `com.freshlink.common.message.notification.NotificationMessage` (`type` = `NOTIFICATION`)
- 권한: inventory IRSA에 이 큐 `SendMessage`가 이미 들어 있다(infra). 코드만 넣으면 된다.

| 칸 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `messageId` | UUID 문자열 | ✓ | **멱등 키.** 팩토리가 만든다. 같은 값이 두 번 와도 알림은 한 번만 생긴다 |
| `type` | `"NOTIFICATION"` | ✓ | 쪽지 종류 (common이 채운다) |
| `createdAt` | ISO-8601 (+09:00) | ✓ | 일이 일어난 시각. 팩토리가 채운다 |
| `kind` | `EXPIRY_IMMINENT` \| `EXPIRED` \| `RESTOCKED` | ✓ | 알림 종류 |
| `storeId` | 숫자 | ✓ | 점포. 유통기한 알림은 이 점포 점주에게 간다 |
| `userId` | 문자열 \| null | | 고객 한 명에게 보낼 때만 (Cognito `sub`). **지금 세 종류는 모두 null** |
| `productId` | 숫자 | ✓ | 상품 |
| `productName` | 문자열 | ✓ | 화면 문구에 쓴다 (notification-service는 상품 표를 모른다) |
| `lotId` | 숫자 \| null | 유통기한 알림만 | lot |
| `expiresAt` | ISO-8601 (+09:00) \| null | 유통기한 알림만 | lot 유통기한 |
| `quantity` | 숫자 | ✓ | 유통기한 알림: 그 lot의 남은 수량. 재입고: 입고 뒤 팔 수 있는 수량 |

예시 (common 테스트 `MessageJsonTest`에 같은 JSON이 있다):

```json
{"messageId":"6f1c2a9e-0000-4000-8000-000000000001","type":"NOTIFICATION",
 "createdAt":"2026-10-31T00:00:00+09:00","kind":"EXPIRY_IMMINENT","storeId":1,"userId":null,
 "productId":15,"productName":"매운 컵라면 115g","lotId":300,
 "expiresAt":"2026-10-31T23:59:59+09:00","quantity":4}
```

```json
{"messageId":"…","type":"NOTIFICATION","createdAt":"2026-11-02T10:00:00+09:00",
 "kind":"RESTOCKED","storeId":1,"userId":null,"productId":15,"productName":"매운 컵라면 115g",
 "lotId":null,"expiresAt":null,"quantity":20}
```

## 4. inventory에서 보내는 법 (태우님)

1. `build.gradle`의 common을 `0.6.0`으로 올린다.
2. `application.yml`에 큐 이름을 더한다: `app.queue.notifications: ${QUEUE_PREFIX}notification-events`
3. 보낼 때는 팩토리를 쓴다. `messageId`·`createdAt`은 팩토리가 채운다.

```java
// 유통기한 스케줄러(LotStatusService.refresh): lot을 IMMINENT로 바꾸는 같은 트랜잭션에서, 바뀐 lot마다
outboxWriter.save(notificationQueue,
        NotificationMessage.expiryImminent(storeId, productId, productName, lotId, expiresAt, quantity));

// EXPIRED로 바뀐 lot마다
outboxWriter.save(notificationQueue,
        NotificationMessage.expired(storeId, productId, productName, lotId, expiresAt, quantity));

// INBOUND 처리: 이 점포·상품의 팔 수 있는 수량이 0 → 1 이상이 되었을 때만
outboxWriter.save(notificationQueue,
        NotificationMessage.restocked(storeId, productId, productName, sellableAfter));
```

지킬 것:

- **상태가 바뀌는 순간에 한 번만 보낸다.** 지금 `refresh()`는 `markImminent`·`markExpired`로 한꺼번에 UPDATE만 하므로, 바뀔 lot을 먼저 조회(예: `status = NORMAL and expiry_date <= now + 24h`)하고 그 lot들만 보낸다. 이미 IMMINENT인 lot은 다시 보내지 않는다. 그러면 "같은 lot은 한 번만"이 저절로 지켜진다(스케줄러가 몇 번 돌아도 상태 전환은 한 번이다).
- 남은 수량이 0인 lot(다 팔렸거나 폐기된 lot)은 보내지 않는다.
- 재입고는 **0에서 올라올 때만** 보낸다. 이미 남아 있던 상품에 입고가 더해지면 보내지 않는다. 신청자가 없으면 notification-service가 아무것도 만들지 않으니 inventory는 신청 여부를 몰라도 된다.
- 반품(RETURN)·예약 취소(RELEASE)로 0에서 다시 생긴 것은 재입고가 아니다. INBOUND에서만 보낸다.
- 쪽지를 큐로 바로 보내지 말고 꼭 Outbox(같은 트랜잭션)로 남긴다. 상태 변경이 되돌려지면 쪽지도 안 나간다.

## 5. notification-service API (화면이 부른다)

모두 gateway `/api/notifications/**`를 지나며 **로그인이 필요하다**(BFF 쿠키). 받는 사람은 gateway가 넣어 주는 사용자 헤더로 정한다. 점주는 자기 계정 알림과 자기 점포 알림을 함께 본다.

| 메서드·경로 | 설명 |
| --- | --- |
| `GET /api/notifications?page=0&size=20` | 내 알림 목록 (최신순, size 최대 50) |
| `GET /api/notifications/unread-count` | 안 읽은 개수 `{"count": 3}` |
| `PATCH /api/notifications/{id}/read` | 하나 읽음 |
| `PATCH /api/notifications/read-all` | 모두 읽음 |
| `GET /api/notifications/stream` | SSE. `event: notification`, `id: <알림 번호>`, `data: <알림 JSON>` |
| `GET /api/notifications/restock/{productId}?storeId=` | 재입고 알림 신청 여부 (고객만) |
| `POST /api/notifications/restock/{productId}?storeId=` | 재입고 알림 신청 (고객만, 두 번 해도 하나) |
| `DELETE /api/notifications/restock/{productId}?storeId=` | 신청 취소 (고객만) |

재입고 알림은 **한 번만** 간다. 알림을 만들 때 그 신청은 지운다. 또 받고 싶으면 다시 신청한다.

## 6. SSE 시간 설정

| 구간 | 끊기는 시간 | 우리 설정 |
| --- | --- | --- |
| CloudFront → ALB | 30초 동안 데이터가 없으면 (origin 응답 타임아웃) | heartbeat 20초 |
| ALB | 60초 유휴 | heartbeat 20초 |
| gateway | 읽기 타임아웃 없음, `text/event-stream`은 모으지 않고 바로 흘림 | 설정 없음 (gateway 테스트로 확인) |
| notification-service | 연결 하나 최대 30분 | 끊기면 브라우저가 3초 뒤 다시 붙고 `Last-Event-ID` 뒤를 받는다 |

파드가 여러 개면 연결된 파드에만 이벤트가 가므로 **파드 1개**로 시작한다(파드가 바뀌어도 다시 붙을 때 놓친 알림은 DB에서 채워진다).

## 7. 화면

- 점주 화면 왼쪽 위, 고객 화면 오른쪽 위에 종 아이콘과 안 읽은 개수가 있다. 누르면 목록이 열리고, 알림을 누르면 읽음이 되고 그 화면으로 간다.
- 새 알림이 오면 sonner 토스트가 뜬다("보기"를 누르면 이동).
- 고객 상품 상세에서 **품절일 때만** "재입고 알림 받기" 버튼이 보인다. 신청하면 "재입고 알림 신청됨 · 취소"로 바뀐다. (태우님 화면 `StoreProductDetailPage`에 김진아가 버튼을 넣었다.)
