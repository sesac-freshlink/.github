# 팀원 가이드 4. 관측성: 지표·로그·추적 보는 법

작성: 김진아 · 2026-10-20 · 대상: 이태우(inventory-service), 김경우(member-service·order-service)

> **한 줄 요약:** dev에서 서비스가 찍는 로그는 Loki(S3, 14일), 요청 수·응답 시간·JVM 지표는 Prometheus(3일), 요청 흐름은 Zipkin에 모이고, 셋 다 **Grafana 대시보드 "FreshLink 서비스" 하나**에서 본다. 서비스 코드는 평소처럼 SLF4J로 로그만 찍으면 되고, traceId는 저절로 붙는다.

설정과 구조는 gitops [`platform/observability/README.md`](https://github.com/sesac-freshlink/gitops/blob/main/platform/observability/README.md), 설치 순서는 infra README 4-14에 있다. 여기는 **쓰는 법**만 적는다.

---

## 1. 무엇이 어디에 얼마나 남나 (dev)

| 종류 | 어디에 | 보관 | 클러스터를 지우면(금요일) |
| --- | --- | --- | --- |
| 서비스 로그 (ERROR 포함) | Alloy → Loki → S3 `freshlink-dev-loki-logs-…` | 14일 | 남는다 |
| 지표 (요청 수·응답 시간·에러율·JVM·DB 풀) | Prometheus (클러스터 디스크) | 3일 | 사라진다 |
| 추적 (traceId별 요청 흐름) | Zipkin (메모리, 최대 10만 건) | 그날 낮까지 (평일 21:00 노드가 꺼지면 파드와 함께 사라진다) | 사라진다 |
| Lambda 로그 (가입 확인, 비용 메일, 켜고 끄기) | CloudWatch Logs | 14일 | 남는다 |

에러 기록이 따로 있는 게 아니라, 로그 중 `"level":"ERROR"`인 줄이 에러 기록이다. prod 관측성은 첫 prod release 날 켠다.

## 2. 여는 법

Grafana·Zipkin은 인터넷에 열려 있지 않다. 클러스터 관리자 권한(지금은 김진아 계정)으로 `kubectl port-forward`를 한 PC에서만 열린다. 그래서 Grafana에는 로그인이 없다. 오른쪽 위 **Sign in**은 무시한다.

> 지금 팀원 계정(`freshlink-dev`)에는 EKS 접근 권한이 없다. 로그나 traceId를 봐야 하면 김진아에게 서비스 이름·시각·traceId를 알려 주고 같이 본다.

PowerShell 창 두 개를 띄워 각각 친다. 창을 닫으면 연결이 끊긴다.

```powershell
aws eks update-kubeconfig --name freshlink-dev-eks --region ap-northeast-2   # 처음 한 번

kubectl -n observability port-forward svc/kube-prometheus-stack-grafana 3000:80   # 창 1 → http://localhost:3000
kubectl -n observability port-forward svc/zipkin 9411:9411                        # 창 2 → http://localhost:9411
```

## 3. 대시보드 "FreshLink 서비스"

http://localhost:3000 → 왼쪽 **Dashboards** → 폴더 **FreshLink** → **FreshLink 서비스**.

맨 위 줄의 칸 세 개로 거른다. 맨 위 가운데 **Search… (Ctrl+K)** 는 대시보드 이름을 찾는 칸이라 로그와 상관없다.

| 칸 | 하는 일 |
| --- | --- |
| 서비스 | 볼 서비스 고르기 (All = 전부) |
| 로그 레벨 | ERROR·WARN·INFO 중 고르기 |
| 로그 검색 (traceId 등) | 넣은 글자가 든 로그 줄만 남긴다. 예: `주문 만료`, `orderId=3`, traceId 32자리. Enter |

| 묶음 | 패널 |
| --- | --- |
| 한눈에 | 초당 요청 수, 5xx 비율, p95 응답 시간, 떠 있는 파드 |
| 요청 (서비스별) | 초당 요청 수, 응답 시간 p95·평균, 에러율(4xx·5xx), API별 요청 표 |
| JVM | 힙, GC, CPU, 스레드, DB 커넥션 풀(Hikari), 재시작 |
| 로그 (Loki) | ERROR 로그 수, 로그 목록 |

시간 범위는 오른쪽 위(기본 **Last 1 hour**). 오래된 로그를 찾을 때는 여기를 늘린다.

## 4. 에러 하나 따라가기

1. **로그 레벨**을 `ERROR`로, **서비스**를 내 서비스로 고른다.
2. 로그 줄을 눌러 펼친다. JSON에 `traceId`가 있다.
3. `traceId` 줄 옆 **Zipkin** 버튼을 누르면 그 요청이 gateway → 내 서비스 → (SQS) → 다른 서비스로 어떻게 지나갔는지, 어디서 얼마나 걸렸는지 보인다.
4. 같은 traceId를 **로그 검색** 칸에 넣으면 그 요청이 남긴 로그가 서비스 상관없이 모두 나온다.

## 5. 직접 쿼리하고 싶을 때 (Explore)

왼쪽 **Explore** → 위쪽 데이터 소스 **Loki**. 라벨은 `namespace`, `app`(서비스 이름), `level`, `pod`, `container`.

```logql
{namespace="freshlink", app="order-service", level="ERROR"}
{namespace="freshlink", app="inventory-service"} |= "RESERVE"
{namespace="freshlink"} |= "6ad733e423174b75e0834380a30bd3ba"
```

지표는 데이터 소스 **Prometheus**에서 `http_server_requests_seconds_count{namespace="freshlink", job="order-service"}`처럼 본다.

## 6. 서비스 개발자가 할 것

| 할 것 | 이유 |
| --- | --- |
| 로그는 SLF4J(`log.info`, `log.error("…", e)`)로 찍는다. `System.out` 쓰지 않는다 | dev에서는 JSON(ECS)으로 바뀌고 traceId가 저절로 붙는다. 비밀번호·토큰·카드 번호는 찍지 않는다 |
| common을 **0.3.0**으로 올린다 (`implementation "com.freshlink:common:0.3.0"`, inventory·order) | Outbox로 보낸 SQS 쪽지가 같은 traceId로 이어진다. 0.2.0이면 SQS 너머가 새 traceId로 끊긴다. 코드·Flyway 변경은 없다 |
| `spring-boot-starter-zipkin`과 yml 설정은 지우지 않는다 (10/20 PR로 들어갔다) | Zipkin 주소와 켜기는 dev 배포 값이 넣는다. PC에서는 꺼져 있다 |

## 7. 안 보일 때

| 증상 | 원인과 할 일 |
| --- | --- |
| 요청 그래프가 **No data** | 그 시간에 API 요청이 없었다. 서비스가 막 다시 떴으면 dev 사이트를 몇 번 눌러 요청을 만들고 1–2분 뒤 Refresh |
| "떠 있는 파드"까지 No data | Prometheus가 서비스를 못 읽는다. `kubectl -n argocd get applications`에서 kube-prometheus-stack이 Healthy인지 |
| 로그가 안 나온다 | 시간 범위와 칸 세 개를 먼저 본다. 그래도 없으면 `kubectl -n observability get pods`에서 alloy·loki가 Running인지 |
| Zipkin 버튼을 눌렀는데 비어 있다 | Zipkin 파드가 다시 떴거나(메모리라 사라짐) 그 서비스 이미지가 10/20 이전 것 |
| SQS 너머가 다른 traceId | 보내는 서비스의 common이 0.2.0 |
