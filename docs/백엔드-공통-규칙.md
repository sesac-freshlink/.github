# 백엔드 공통 규칙 (뼈대·오류 처리·서비스 간 통신)

> 2026-10-15. 작성: 문영훈. `백엔드-공통작업-인수인계.md`의 작업 A·B를 진행하면서 정한 것과, 담당자가 기능을 만들 때 그대로 따르면 되는 규칙만 적었다. 쪽지 형식은 인수인계 3-3이 진실이고 여기엔 없다.

## 1. 버전

| 항목 | 버전 |
|---|---|
| Spring Boot | 4.0.8 |
| Java | 21 |
| Gradle Wrapper | 9.8.1 |
| Spring Cloud (gateway) | 2025.1.3 |
| Jackson (common) | 3.x (Boot BOM) |
| MySQL (Testcontainers) | 8.4 |

네 서비스 레포 `dev`에 뼈대가 합쳐져 있다 (10/15). 버전을 바꾸면 네 레포를 같이 바꾼다.

## 2. gateway는 Spring Cloud Gateway **WebMVC**판

- 처음 규칙은 WebFlux였으나 **WebMVC(서블릿)판으로 바꿨다** (10/15 팀 합의). 이유: 팀이 배운 스택이 서블릿 MVC이고 서비스 3개와 같은 바탕이라 전원이 읽고 고칠 수 있다.
- 의존성 `spring-cloud-starter-gateway-server-webmvc`. 설정 키는 `spring.cloud.gateway.server.webmvc.*` (`server.webflux`가 아니다).
- 필터는 평소 서블릿 `Filter`, Security는 `SecurityFilterChain`. `Mono`·`Flux`를 쓰지 않는다.

## 3. 테이블 관리: 세 서비스 모두 Flyway

- member·order·inventory 전부 **Flyway**로 테이블을 만든다 (10/15 결정). `src/main/resources/db/migration/V1__init.sql`부터 순서대로. 앱이 뜰 때 Flyway가 안 적용된 파일을 실행한다.
- `spring.jpa.hibernate.ddl-auto`를 쓰지 않는다 (기본값 `none` 그대로). 한 번 적용된 파일은 고치지 않고 `V2__…`를 추가한다.
- 파일이 하나도 없으면 "No migrations found" 경고만 찍고 정상으로 뜬다.

## 4. 로컬에서 띄우기

| 상황 | 방법 |
|---|---|
| DB 없이 바로 띄우기 | Docker Desktop 켜고 `src/test/java/.../Test<Service>Application` 실행. Testcontainers가 MySQL 8.4 컨테이너를 띄워 붙인다. 환경 변수 불필요. main 소스 변경이 그대로 반영된다. 끄면 컨테이너와 데이터가 사라진다 |
| dev RDS에 붙기 | `DB_URL`·`DB_USERNAME`·`DB_PASSWORD` 환경 변수 주고 `<Service>Application` 실행 |
| 서비스 두 개 이상 동시에 | 전부 8080이라 겹친다. Run Configuration 환경 변수에 `SERVER_PORT=8081`처럼 준다. yml은 안 건드린다 |
| gateway | DB 없음. `GatewayApplication` 바로 실행 |

확인: `GET http://localhost:8080/actuator/health` → `{"status":"UP"}`.

개발도 dev RDS·dev SQS·dev Cognito에 붙는다 (인수인계 1-2). `local-dev` 레포(Docker Compose)는 쓰지 않는다. DB 없이 뜨는지만 볼 때 위 `Test<Service>Application`을 쓴다.

## 5. 환경 변수

인수인계 1-2 표 그대로. 코드·설정 파일에 값을 적지 않는다.

| 변수 | 보관 | 쓰는 서비스 |
|---|---|---|
| `SPRING_PROFILES_ACTIVE` | Helm values | 전부 |
| `DB_URL`, `DB_USERNAME` | Helm values (또는 Secret) | member·order·inventory |
| `DB_PASSWORD` | **Secrets Manager** → External Secrets → 파드 | member·order·inventory |
| `QUEUE_PREFIX` | Helm values | order·inventory |
| `COGNITO_ISSUER_URI`, `COGNITO_CLIENT_ID` | Helm values | gateway |

비밀값은 `DB_PASSWORD`뿐이다. GitHub Actions 시크릿에는 두지 않는다 (빌드 때 필요 없다).

## 6. 오류 처리

### 모양은 common, 목록과 핸들러는 서비스

| 위치 | 파일 | 역할 |
|---|---|---|
| common `error/` | `ErrorCode`(interface), `BusinessException`, `ErrorResponse`(record) | 응답 **모양**만. Spring 없음 |
| 각 서비스 `error/` | `<Service>ErrorCode`(enum), `GlobalExceptionHandler` | 오류 **목록**과 변환 |

서비스 코드에서는 한 줄이면 끝이다.

```java
throw new BusinessException(OrderErrorCode.ORDER_NOT_FOUND);
```

응답은 항상 세 키다. 프론트는 `code`로 분기하고 `message`를 보여 준다.

```json
{"code": "ORDER_NOT_FOUND", "message": "주문이 없습니다", "traceId": "4bf92f3577b34da6"}
```

| 예외 | 상태 | code |
|---|---|---|
| `BusinessException` | enum의 status | enum 이름 |
| `@Valid` 실패 | 400 | `VALIDATION_ERROR` (message에 필드별 사유) |
| Spring이 상태를 아는 예외 (없는 경로, 405 …) | 그 상태 | `NOT_FOUND`, `METHOD_NOT_ALLOWED` … |
| 그 밖 | 500 | `INTERNAL_ERROR` (원인은 로그에만, 응답엔 안 나감) |

- 오류 코드를 추가할 땐 enum에 한 줄 (`XXX(404, "메시지")`). 핸들러는 안 건드린다.
- `traceId`는 로그 MDC에서 꺼낸다. Micrometer Tracing을 켜면 자동으로 채워지고, 로그·Zipkin과 같은 값이다. 꺼져 있으면 `""`.

### common에 ExceptionHandler를 두지 않은 이유

핸들러 40줄을 서비스 3개에 복사했다. 서비스가 3개라 복사가 더 싸고, common이 Spring 버전에 묶이지 않는다. 공통 핸들러(`common-web` 모듈)로 옮길 만한 때:

- 핸들러 수정이 반복될 때. 예: traceId 꺼내는 방식이나 400 메시지 형식을 바꿨는데 서비스 3개 PR을 따로 내야 하는 일이 두 번 이상 생김
- 서비스가 늘어날 때. 예: logistics-simulator나 알림 서비스가 추가돼 같은 핸들러를 네 번째 복사하게 됨

## 7. 서비스 간 통신

### 원칙: 명령은 큐, 조회는 동기 HTTP

| 종류 | 예 | 방식 | 이유 |
|---|---|---|---|
| **명령** (상대 상태를 바꾼다) | 재고 예약·확정·해제, 입고, 폐기 | SQS 쪽지 + Outbox | 상대가 죽어 있어도 요청이 큐에 남는다. 잃으면 안 되는 요청 |
| **조회** (지금 답이 필요하다) | "이 점포 영업 중?" | 동기 HTTP (`RestClient`) | 큐로 하면 답을 기다리는 코드가 더 복잡하고 느리다. 못 받으면 사용자가 새로고침하면 되는, 잃어도 되는 요청 |

지금 설계는 **동기 호출이 0개**다. 조회가 필요할 자리를 이렇게 피해 놨다.

- 사용자 정보 → gateway가 `X-User-Id`·`X-User-Role`·`X-Store-Id` 헤더로 넘긴다. 서비스는 member에 묻지 않는다.
- 상품 가격 → inventory가 `RESERVED` 쪽지에 `unitPrice`를 실어 보낸다. order는 주문 시점 가격을 자기 DB에 **스냅샷**으로 저장한다 (나중에 가격이 바뀌어도 주문서는 그때 가격).
- 한 화면에 두 서비스 데이터(매출+재고) → 프론트가 gateway 통해 API 2개를 부른다.

### 동기 호출이 필요해질 수 있는 자리

| 후보 | 누가 → 누구 | 흔한 해법 |
|---|---|---|
| 주문 전 점포 영업 여부·휴무 확인 | order → member | **동기 HTTP 1개** (가장 먼저 생길 후보) |
| 주문서 미리보기 (장바구니 합계) | — | 프론트가 inventory 직접 조회. 백엔드 호출 없음 |
| 주문 내역에 점포 이름·주소 | order → member | 주문 시 점포명 스냅샷 저장 |
| 쿠폰·할인 (추가된다면) | order → member | 동기 HTTP |

### 동기 호출이 생기면 이렇게 (호출하는 쪽 레포에만, 15줄 안팎)

1. `RestClient` 빈 하나를 `config/`에 만든다. 연결·읽기 타임아웃을 준다 (예: 2초·3초). 안 주면 상대가 느릴 때 내 스레드가 같이 묶인다.
2. 상태 핸들러를 건다. 상대가 보낸 `ErrorResponse` JSON을 읽어 `BusinessException`으로 던진다. 그러면 기존 `GlobalExceptionHandler`가 받아서 상대의 `code`·상태를 프론트까지 그대로 전달한다 (order 응답에 `MEMBER_NOT_FOUND` 404).
3. 상대가 아예 죽어 있을 때(연결 실패, 타임아웃)를 위해 enum에 `SERVICE_UNAVAILABLE(503, "잠시 후 다시 시도해 주세요")` 한 줄 추가.
4. 상대 주소는 `${MEMBER_SERVICE_URL:http://member-service:8080}`처럼 설정 값으로. 코드에 안 적는다.

```java
@Bean
RestClient memberClient(RestClient.Builder builder, @Value("${app.member-service.url}") String url) {
    return builder.baseUrl(url)
        .defaultStatusHandler(HttpStatusCode::isError, (req, res) -> {
            ErrorResponse body = MessageJson.MAPPER.readValue(res.getBody(), ErrorResponse.class);
            throw new BusinessException(remote(body, res.getStatusCode().value()));   // code·status를 상대 것 그대로
        })
        .build();
}
```

### 동기 호출에 재시도·서킷 브레이커를 안 넣는 이유

- 에러 처리는 **실패를 깔끔하게 알리는 것**이지 요청을 보관해 주지 않는다. 상대가 몇 분 죽어 있으면 조회는 실패하고, 사용자가 다시 시도한다. 그래도 되는 요청만 동기로 보낸다.
- 큰 서비스는 여기에 서킷 브레이커(상대가 계속 죽어 있으면 호출을 끊어 나까지 죽는 걸 막음)와 폴백(못 받으면 캐시값·빈 칸으로 화면은 보여 줌)을 얹는다 (Resilience4j). 동기 호출이 0개인 지금은 필요 없고, 첫 호출이 생겨도 MVP에선 타임아웃만으로 충분하다. 시연 전 부하 시험에서 문제가 보이면 그때 넣는다.
