# 팀원 가이드 6. 디스코드 알림이 오면 (배포 알림 · DLQ 알림)

작성: 김진아 · 2026-10-28 · 대상: 이태우(inventory-service), 김경우(member-service·order-service)

> **한 줄 요약:** 디스코드에는 알림 채널이 두 개 있다. **배포 채널**은 GitHub Actions가 배포·승격·클러스터 켜고 끄기 결과를 보내고, **DLQ 채널**은 AWS가 "처리 못 한 재고 쪽지가 쌓였다"를 보낸다. dev에서 내 서비스가 실패하면 **내가 고친다.** 인프라가 원인이거나 prod면 **김진아**가 맡는다.

명령은 모두 Windows PowerShell 기준이다. 이 문서는 "알림을 보고 무엇을 하나"만 다룬다. 배포가 어떻게 흘러가는지는 [가이드 2의 6장](팀원-가이드-2-인프라-배포.md#6-배포-흐름-a부터-z까지), 로그 보는 법은 [가이드 4](팀원-가이드-4-관측성.md)에 있다.

## 1. 두 채널 한눈에

| | 배포 채널 | DLQ 채널 |
| --- | --- | --- |
| 누가 보내나 | GitHub Actions (`actions/notify`, 보낸 이 `freshlink-ci`) | AWS (CloudWatch 경보 → SNS → Lambda `freshlink-<env>-dlq-alert`) |
| 언제 오나 | 서비스 dev 배포·prod 승격, 프론트 dev·prod 배포, dev·prod 클러스터 켜고 끄기가 끝날 때마다 (성공도 온다) | 공용 DLQ에 쪽지가 1개라도 생길 때, 그리고 다시 비었을 때 |
| 웹훅 주소 | GitHub 조직 비밀 `DEPLOY_WEBHOOK_URL` | Secrets Manager `freshlink-<env>-dlq-webhook` |
| dev에서 보는 사람 | 그 서비스 담당자 (인프라 원인이면 김진아) | 재고 담당 이태우 (원인 서비스 담당자와 같이) |
| prod에서 보는 사람 | 김진아 | 김진아 |

배포 채널에 오는 알림은 세 종류다. PR 빌드는 알림을 보내지 않는다.

| 첫 줄 제목 | 보내는 곳 | 실패하면 |
| --- | --- | --- |
| `<서비스> dev 배포`, `<서비스> prod 승격` | 서비스 레포 → `.github` `spring-build.yml` | dev는 그 서비스 담당자, prod는 김진아 (3-1, 3-2) |
| `frontend dev 배포`, `frontend prod 배포` | frontend 레포 `frontend-deploy.yml` | dev는 프론트 코드 담당 김경우, prod는 김진아 (3-1) |
| `dev 클러스터 create`·`destroy`·`nat-on`·`nat-off` 등, `prod 클러스터 …` | infra 레포 `dev-cluster.yml`(평일 켜고 끄기 예약·수동 실행. prod는 `prod-cluster.yml`이 같은 파일을 부른다) | 김진아 (3-1 표 마지막 줄) |

## 2. 배포 채널 알림 읽기

알림은 이런 모양이다.

```text
❌ 실패 inventory-service dev 배포
inventory-service · a1b2c3d · <GitHub 아이디> (push)
실패한 단계: 테스트
> InventoryServiceTest > reserve_fifo() FAILED
https://github.com/sesac-freshlink/inventory-service/actions/runs/123456789
```

| 줄 | 뜻 |
| --- | --- |
| 첫 줄 | 결과(✅ 성공 · ❌ 실패 · ⚪ 취소 · ⏭️ 건너뜀)와 무엇을 했는지. `<서비스> dev 배포`, `<서비스> prod 승격`, `dev 클러스터 create` 같은 식 |
| 둘째 줄 | 레포 · 커밋 7자리(= 이미지 태그) · 누가(이벤트). 예약 실행이면 `예약` |
| `실패한 단계:` | 실패일 때만. 빨간불이 난 단계 이름 |
| `>` 줄 | 실패일 때만. 로그의 오류 메시지 최대 3개(하나에 300자까지). 못 읽으면 이 줄 없이 링크만 온다 |
| 마지막 줄 | Actions 실행 링크. 자세한 건 여기서 본다 |

`⏭️ 건너뜀`은 예약 실행이 너무 늦게 와서 일부러 안 한 것이다(예: "예약이 늦게 와서 건너뛰었다"). 할 일이 없다. `⚪ 취소`는 누가 실행을 멈췄거나 새 실행에 밀린 것이다.

## 3. 배포 실패: 누가 무엇을

### 3-1. dev 배포 실패 → 그 서비스 담당자

1. 알림의 `실패한 단계`와 `>` 줄을 먼저 본다. 아래 표로 내 일인지 인프라 일인지 가른다.
2. 내 일이면 실행 링크로 **Actions 로그**를 열어 원인을 찾고, 로컬에서 `.\gradlew build`로 재현해 고친다.
3. 고친 PR을 `dev`에 다시 합친다. **dev는 되돌리지 않는다.** 새 이미지로 덮인다([가이드 2의 6-5](팀원-가이드-2-인프라-배포.md#6-5-되돌리기-롤백)).
4. Actions는 ✅인데 화면이 그대로이거나 파드가 계속 재시작하면 **ArgoCD**에서 그 서비스 상태·이벤트를 보고, **Grafana → Loki**에서 로그를 본다([가이드 4](팀원-가이드-4-관측성.md)).

| `실패한 단계` · 오류 메시지 | 누구 일 | 할 일 |
| --- | --- | --- |
| 빌드·테스트 단계, `FAILED`, 컴파일 오류 | **나** | 로컬에서 재현해 고친 PR을 `dev`에 |
| `401 Unauthorized` (maven.pkg.github.com) | 김진아 | common 패키지 권한. 알림 링크를 보낸다 |
| `Could not assume role`, OIDC 오류 | 김진아 | AWS 인증 문제 |
| ECR push 실패 | 김진아 | 이미지 창고 문제 |
| `gitops push가 계속 실패했다` | 김진아 | gitops 커밋 실패 |
| ✅인데 ArgoCD가 `Degraded`/`OutOfSync`, 앱이 시작하다 죽음 | 먼저 **나** (Loki 로그) | 앱 오류(설정 키 이름, 예외)면 내가 고친다. DB·큐·비밀값 연결 실패면 김진아 |
| `frontend dev 배포`가 `npm run lint`·`npm test`·`build` 단계에서 실패 | **김경우** | 로컬에서 같은 명령으로 재현해 고친 PR을 frontend `dev`에 |
| `frontend … 배포`가 `배포 값 확인`·`S3에 올리기`·`CloudFront 무효화` 단계나 AWS 인증에서 실패 | 김진아 | 배포 권한·버킷 문제 |
| `dev 클러스터 …`·`prod 클러스터 …` 알림이 실패 | 김진아 | 예약 켜고 끄기(NAT·노드) 문제. 그 시간 dev가 안 될 수 있다. 주말에 내가 켰다면 [가이드 5의 7장](팀원-가이드-5-주말-dev-켜기.md#7-문제가-생기면) |

애매하면 고치려 들지 말고 3-3처럼 김진아에게 링크를 보낸다.

### 3-2. prod 승격 실패 → 김진아

`<서비스> prod 승격`이 ❌이면 김진아가 본다. release를 김진아가 하기 때문이다. 필요하면 김진아가 gitops 승격 커밋을 되돌린다([가이드 2의 6-5](팀원-가이드-2-인프라-배포.md#6-5-되돌리기-롤백)). 원인이 내 코드면 고친 PR을 **`dev`로** 올려 다음 release로 다시 내보낸다. `main`에 직접 올리지 않는다.

자주 나오는 원인 하나: release PR을 Squash로 합쳐 "ECR에 없다"로 멈춘 경우. release PR은 꼭 **Create a merge commit**으로 합친다([가이드 2의 6-4](팀원-가이드-2-인프라-배포.md#6-4-prod로-올리기-할-일-15-예정)).

### 3-3. 김진아에게 넘길 때

디스코드 알림 메시지를 그대로 전달(또는 링크 복사)하고 한 줄만 붙인다. "인프라 쪽 같아요, 로컬 빌드는 통과해요"처럼 내가 확인한 것을 적는다.

## 4. DLQ 채널 알림 읽기

재고 쪽지(SQS)를 서비스가 **3번 받고도 처리하지 못하면** DLQ(처리 못 한 쪽지를 모아 두는 큐)로 옮겨진다. 경보는 공용 DLQ 두 개에만 걸려 있다.

| 큐 이름 | 무엇이 쌓이나 |
| --- | --- |
| `<env>-inventory-commands-dlq.fifo` | order → inventory 명령(예약·확정·취소) 중 inventory가 처리 못 한 것 |
| `<env>-inventory-results-dlq` | inventory → order 결과 중 order가 처리 못 한 것 |

알림은 이런 모양이다.

```text
🚨 [dev] DLQ에 쪽지가 쌓였습니다
큐: dev-inventory-commands-dlq.fifo
이유: Threshold Crossed: ...
할 일: 서비스 로그로 원인을 고친 뒤 infra README 4-16 순서로 재처리합니다.
```

DLQ를 비우거나 재처리가 끝나면 `✅ [dev] DLQ가 비었습니다`가 한 번 더 온다. 머리의 `[dev]`·`[prod]`로 환경을 구분한다.

- **`[prod]`면 김진아가 맡는다.** 팀원 프로필로는 prod 큐를 만질 수 없다.
- **`[dev]`면** 큐 이름으로 어느 서비스가 실패했는지 본다. `commands`면 inventory-service(이태우), `results`면 order-service(김경우)가 원인을 찾는다.
- 개발자별 DLQ(`dev-<아이디>-...`)에는 경보가 없다. 로컬에서 내 큐로 시험할 때는 각자 콘솔에서 본다.

## 5. DLQ 재처리 (dev)

원본 절차는 [infra README 4-16](https://github.com/sesac-freshlink/infra/blob/main/README.md#4-16-dlq-알림discord과-재처리-김진아)이다. 여기에는 팀원이 dev에서 하는 부분만 옮겼다. 순서는 **개수 확인 → 내용 보기 → 원인 고치기 → 재처리**다.

AWS 프로필 `freshlink-dev`가 내 PC에 있어야 한다. 없으면 [개발환경-접속.md 1-2](개발환경-접속.md#1-2-aws-로그인-프로필-freshlink-dev)대로 먼저 만든다.

**(1) 준비와 개수 확인.** `$dlqName`에 알림에 나온 큐 이름을 넣는다.

```powershell
$env:AWS_PROFILE = "freshlink-dev"
$dlqName = "dev-inventory-commands-dlq.fifo"   # 알림의 '큐:' 값
$dlq    = aws sqs get-queue-url --queue-name $dlqName --query QueueUrl --output text
$dlqArn = aws sqs get-queue-attributes --queue-url $dlq --attribute-names QueueArn --query Attributes.QueueArn --output text

aws sqs get-queue-attributes --queue-url $dlq --attribute-names ApproximateNumberOfMessages
```

**(2) 내용 보기.** 지우지 않는다. 30초 뒤 다시 보인다.

```powershell
aws sqs receive-message --queue-url $dlq --max-number-of-messages 10 --visibility-timeout 30 --attribute-names All --message-attribute-names All
```

**(3) 원인 고치기.** 쪽지 본문의 `messageId`·`storeId`로 Grafana → Loki에서 리스너 로그를 검색해 왜 실패했는지 본다([가이드 4](팀원-가이드-4-관측성.md)). 고친 PR을 `dev`에 합치고 배포 채널에 ✅가 온 것을 확인한다.

> **원인을 고치기 전에 재처리하지 않는다.** 그대로 3번 더 실패하고 DLQ로 돌아온다.

**(4) 재처리.** 목적지를 적지 않으면 원래 큐로 되돌아간다.

```powershell
aws sqs start-message-move-task --source-arn $dlqArn

# 진행 상황. Status가 COMPLETED이고 ApproximateNumberOfMessagesMoved가 (1)의 숫자면 끝
aws sqs list-message-move-tasks --source-arn $dlqArn
```

끝나면 DLQ 채널에 `✅ [dev] DLQ가 비었습니다`가 온다(5분 안).

같은 쪽지가 다시 들어가도 서비스가 `processed_message`로 걸러서 재고가 두 번 바뀌지 않는다([가이드 1](팀원-가이드-1-common.md)). 그래서 재처리는 안전하다.

**비우기(purge)는 하지 않는다.** 되돌릴 수 없다. 시험 쪽지라서 버려도 된다고 확신하면 (2)의 내용을 스레드에 남기고 김진아에게 먼저 말한다.

## 6. 물어볼 때

- 디스코드 알림을 그대로 전달하고, **무엇을 확인했는지** 한 줄 붙인다.
- 배포 실패면 커밋 7자리, DLQ면 큐 이름과 (1)의 개수, (2)에서 본 `messageId` 하나.
- prod 알림은 보고만 있어도 된다. 김진아가 스레드에 처리 결과를 남긴다.
