**왜 하나:** prod를 남에게 보여 줄 때 점주 대시보드(주문 내역·매출·판매 순위), 고객 주문 내역, 알림 종이 비어 있으면 데모가 안 된다. 사람이 손으로 주문하지 않아도 prod를 켜 두면 하루 동안 입고 → 주문 → 결제 → 픽업 준비 → 픽업이 저절로 쌓이게 한다. dev는 개발용 시험 데이터만 두고, prod는 점포·고객·상품을 늘려 다양하고 풍부하게 만든다. 대형 부하 테스트가 아니다(30개 점포 합쳐 하루 100–200건, 2차 문서 맨 위 규칙의 "시뮬레이션"과 다르다).

**1-1. prod 데이터 늘리기 (infra 시드, 김진아, 먼저 한다)**

시뮬레이터는 여기서 만든 점포·고객으로 돈다. 데모는 서울만 보여 주므로 점포 30곳을 모두 서울에 둔다. 나중에 지도 API를 넣어 "현재 위치 기준 가까운 점포"를 시연할 예정이고 시연 장소가 **청년취업사관학교 영등포캠퍼스(서울 영등포구 선유로9길 30, 문래동)**라서, 30곳 중 10곳은 문래동 근처(영등포구, 시연 장소에서 약 2km 안)에 둔다. (11/5 사용자 결정, 10곳 계획을 바꿈)

- [ ] 점포: prod를 3곳 → 30곳으로 늘린다. `scripts/seed/prod-member.sql`에 ID 4–30(store_code S4–S30)과 이름·주소·위도·경도를 추가한다. 모두 `SEOUL`(비로그인 기본 지역). 점포는 점주가 이어져야 ACTIVE가 되므로 점주 계정도 27개 더 만든다(`seed-cognito.ps1 -Env prod`의 `$ownerNames`에 아래 영문 이름 추가, 이메일 형식은 지금 prod와 같은 `<지점 영문>@freshlink.co.kr`, 어디에도 "test"를 넣지 않는다). 점주 비밀번호는 지금처럼 30명 같은 값(`-SetOwnerPassword`).
- [ ] 위도·경도: member `store` 표에 이미 `latitude`·`longitude`(DECIMAL(9,6), V2)가 있고 `StoreDetailResponse`가 내려 준다. 시드 SQL에서 이 두 칸을 같이 채운다(지금 1–3번도 비어 있으니 같이 채운다). 아래 표의 좌표는 근처 역 기준 **대략값**이다. 시드 PR을 만들 때 도로명 주소가 실제로 있는지 확인하고, 주소를 지오코딩(카카오·네이버 지도 주소 검색)해 소수 6자리 좌표로 바꾼다. 시연 장소 좌표도 같이 구해 둔다(지도 화면 시험용).
- [ ] 지도 API용으로 남겨 둘 것: "가까운 점포" 목록(위도·경도를 받아 거리순)은 아직 없다. 지도 기능을 할 때 member API(예: `GET /stores?lat=&lng=&radius=`)를 따로 정한다. 시드는 좌표만 맞게 넣어 두면 된다.
- [ ] 가상 고객: prod Cognito에 **100명**을 만든다(dev는 지금처럼 몇 명만). 한국 이름, 이메일·이름 어디에도 "test"를 넣지 않는다. `AdminCreateUser`를 메일 안 보내기(`MessageAction SUPPRESS`)로, `email_verified=true`, 그룹 `CUSTOMER`, 영구 비밀번호. 가입 Lambda가 돌지 않으므로 member 행(role CUSTOMER)도 시드 SQL로 넣는다. 고객마다 단골 점포 1–2곳을 정한다(아래 "고객 나누기").
- [ ] 자격: 비밀번호는 Secrets Manager `freshlink-prod-seed-accounts`에 지금처럼 같이 둔다(사람이 데모 때 고객으로 로그인할 수 있게). 시뮬레이터에는 비밀번호가 필요 없고 고객 sub·단골 점포만 필요하다 → 비밀 `freshlink-prod/simulator/customers`(JSON) → External Secrets → 환경 변수. dev도 같은 모양 `freshlink-dev/simulator/customers`.
- [ ] 시뮬레이터 IRSA는 SQS 보내기만 있으면 된다(Secrets Manager는 ESO가 읽는다). ESO가 새 비밀을 읽을 수 있는지 정책을 확인한다.

10곳일 때 40명(점포당 단골 4명 이상)이었다. 30곳에 같은 비율이면 120명이지만, 고객 1명이 단골 1–2곳(평균 1.5곳)이라 100명이면 점포당 평균 단골 5–6명이 된다. 시연은 문래 근처에서 하므로 그쪽을 두껍게 둔다.

**1-2. 시뮬레이터 코드 (logistics-simulator, 김진아)**
- [ ] `@Scheduled` + 설정값 `simulator.schedule.*`로 위 흐름을 1-1의 점포 30곳·고객 100명으로 돈다. 파드 1개라 ShedLock은 쓰지 않는다. DB가 없으므로 진행 중인 주문은 메모리에만 둔다(파드가 다시 뜨면 그날 남은 픽업 처리만 빠진다. 입고는 고정 `shipmentId`라 다시 보내도 된다).
- [ ] 유통기한을 고정 날짜(지금 preset 10/09·10/20) 대신 "오늘 + N일"로 계산한다. 분류별 기본값: 도시락·김밥·샌드위치·샐러드 0–1일, 유제품·디저트 3–10일, 빵 2–4일, 과일·신선식품 3–7일, 음료 30–90일, 라면·즉석식품 90–180일. 점포마다 1–2개 lot은 오늘 마감(임박 알림), 1개는 어제 마감(경과 알림·폐기 화면)으로 넣는다.
- [ ] 입고량: 점포마다 30개 상품 중 20–30개를 고르고 수량 5–30개. 점포별로 seed(점포 ID + 날짜)를 고정한 난수라 같은 날 다시 돌려도 같은 값이 나온다.
- [ ] 주문: 고객 1명이 단골 점포 1–2곳에서 상품 1개·수량 1–3개(order API 최대 5). 재고는 inventory `GET /stores/{storeId}/products`(클러스터 안 `http://inventory-service:8080`)로 판매 중인 것만 고른다. 선착순 상품은 고르지 않는다.

### 유통기한 기준 할인 (11/4 멘토링, 김경우와)

**왜 하나:** 기한이 가까워 버려질 상품을 싸게 팔면 점주는 폐기를 줄이고 고객은 싸게 산다. 신선식품 서비스의 주제와 가장 잘 맞는 기능이다.

**정할 것 (먼저 한다)**
- 할인 규칙: 고정 규칙(예: 기한 24시간 안 20%, 6시간 안 40%)으로 갈지, 점주가 상품·lot마다 정할지.
- 할인 기준 lot: 고객이 먼저 받는 lot(FEFO, 상세의 `nearestExpiry`와 같은 lot)의 기한으로 정한다. 할인가로 산 주문이 다른 lot에서 빠지지 않는지 예약 순서와 맞춘다.
- 결제 금액: order는 inventory가 예약 성공(RESERVED) 쪽지에 담는 `unitPrice`로 주문 금액을 정한다(화면이 넘기는 가격은 표시용). 그래서 inventory가 예약할 때 할인 단가를 `unitPrice`로 보내면 쪽지 형식을 바꾸지 않고 결제 금액이 할인가가 된다.
- 섞인 주문: 한 주문이 할인 lot과 일반 lot에 걸치면 단가를 하나로 정해야 한다. 할인 lot 수량까지만 할인가로 팔지, 평균 단가를 쓸지 김경우와 정한다.

- [ ] 주문 화면으로 넘기는 값에 할인가를 담는다(표시용. 실제 금액은 서버의 `unitPrice`. 김경우 주문 화면과 맞춘다).

**김경우에게 요청 (김경우 블록)**
- 주문·결제 금액이 화면 값이 아니라 RESERVED의 `unitPrice`로 계산되는지 확인한다. 주문 화면·주문 내역에 "할인" 표시를 넣을지 정한다.

- **완료 기준:** 기한이 가까운 상품이 고객 화면에 할인가로 보이고, 그 값으로 결제·매출이 맞게 남는다.

### 고객 화면 무한 스크롤·당겨서 새로고침 (11/4 멘토링)

**왜 하나:** 고객 화면은 핸드폰 기준이라 페이지 번호보다 스크롤로 이어 보고, 당겨서 새로고침하는 앱 방식이 자연스럽다. 점포 10곳·상품이 늘면 한 번에 다 받는 지금 방식이 무거워진다.

**정할 것:** 적용 범위가 이태우 화면(점포 상품 목록·상세)만인지, 고객 화면 전체(김경우 주문 내역 등)의 공통 기준인지. 공통이면 무한 스크롤·당겨서 새로고침 훅을 `shared`로 올리고 김진아 공통 영역과 맞춘다.

- [ ] inventory: 고객 상품 목록 `GET /stores/{storeId}/products`에 `page`·`size`를 더한다. 검색·카테고리·추천·신상품·정렬과 같이 동작하게 한다. 지금처럼 전체를 주는 호출(시뮬레이터가 쓰는 방식)이 깨지지 않게 기본값을 정한다.
- [ ] frontend: 상품 목록을 아래까지 내리면 다음 묶음을 불러온다(TanStack Query 무한 쿼리). 끝이면 더 부르지 않는다.
- [ ] frontend: 상품 목록·상세에서 아래로 당기면 다시 읽는다.
- **완료 기준:** 핸드폰 크기에서 상품 목록이 끊김 없이 이어지고, 당기면 새 재고가 보인다. 필터·정렬을 바꾸면 처음부터 다시 불러온다.

### 주변 점포 재고 확인 (11/4 멘토링, 김진아·김경우와)

**왜 하나:** 품절이면 고객이 그냥 떠난다. 가까운 점포에 남은 재고를 보여 주면 다른 점포에서 살 수 있다.

**정할 것:** 상품 상세(품절일 때)에 둘지, 구매(주문) 화면에 둘지(회의 메모 "제품창 or 구매창"). 위치 권한을 거부하면 같은 지역 점포로 보여 준다.

- [ ] inventory (이태우): 상품 하나의 점포별 구매 가능 수량 API(공개, 재고가 있는 점포만).
- [ ] frontend (이태우): "근처 ○○점에 N개 있어요"를 거리순으로, 누르면 지도(김경우 점포 상세 지도를 다시 쓴다).

**요청 (각자 블록)**
- 김진아: 위 API의 gateway 공개 경로. 지금 공개 경로 모양(`/stores/{storeId}/products…`)에 맞지 않아 라우트·공개 허용을 더해야 한다.
- 김경우: 점포 목록에 좌표를 넣거나 근처 점포 API를 둔다(지금 좌표는 점포 상세에만 있다).
- 데이터: prod 서울 30곳(김진아 1-1, 시드에 위도·경도 포함)에 점포마다 다른 재고가 있어야 시연된다.

- **완료 기준:** 품절 상품에서 재고가 있는 가까운 점포가 거리순으로 보이고, 눌러서 그 점포 상품으로 갈 수 있다.

### 점주 대시보드 메뉴 구성·기능 협의 (11/4 멘토링, 김경우·김진아와)
- [ ] 지금 점주 메뉴(재고·변동 이력·임박·폐기·주문·매출)를 정리하고, 첫 화면에 "오늘 할 일"(임박·경과 lot, 안전재고 부족, 곧 소진될 상품, 새 주문, 오늘 매출)을 모은 구성안을 만든다.
- [ ] 구성안으로 협의하고 정한 메뉴·화면을 이 문서에 적는다. 매출 카드는 김경우, 레이아웃은 김진아 공통 영역.
- [ ] 정한 대로 재고 쪽 카드·이동 버튼을 만든다(재고 소진 예상, 경과 lot 수 등은 이미 있는 API를 쓴다).
- AI 브리핑은 11/4에 일단 제외했다.
- **완료 기준:** 점주 메뉴·첫 화면 구성이 정해져 이 문서에 적혀 있고, 재고 쪽 카드에서 해당 화면(재고·임박·폐기)으로 바로 갈 수 있다.

### 고객 화면 접근성 (11/4 멘토링, 이태우 화면)
- [ ] 점포 상품 목록·상세: 키보드로 모든 버튼·칩에 갈 수 있고, 이미지에 대체 텍스트, 아이콘 버튼에 이름, 배지 색 대비(D-day·추천·선착순)를 확인한다.
- [ ] 스크린 리더로 상품 한 줄이 "상품명, 가격, 남은 수량, 배지" 순으로 읽히는지 본다.
- **완료 기준:** 마우스 없이 키보드만으로 상품을 골라 상세까지 가고 구매하기를 누를 수 있다.

### UI 기준 적용 (11/4 멘토링, 공통)
- [ ] 디자인 토큰 구조(색·간격·글자)가 정해지면 이태우 화면(점주 재고·변동 이력·임박·폐기, 고객 상품 목록·상세)에 적용한다. 토큰을 누가 먼저 만드는지 정해야 순서가 나온다.
- **완료 기준:** 이태우 화면에 색·간격·글자 임의값이 남지 않고 모두 토큰을 쓴다.

### 픽업 QR 승인 (11/4 멘토링)

**왜 하나:** 고객이 주문 여러 건을 한 번에 받아 갈 때, 점주가 주문을 하나씩 찾지 않고 QR 한 번으로 그 고객의 미픽업 주문을 확인하고 골라서 픽업 완료로 바꾼다.

**흐름 (설계안, 확정 전)**
1. 고객(모바일) 주문 내역 [픽업 QR] → 그 고객의 미픽업 주문을 묶은 QR. QR 안은 주문번호가 아니라 몇 분만 쓰는 일회용 표가 든 점주 화면 주소다.
2. 점주가 핸드폰 기본 카메라로 찍는다 → 핸드폰에는 "컴퓨터 화면에서 확인해 주세요"만 뜬다(승인은 핸드폰에서 하지 않는다).
3. 같은 점주 계정으로 열린 컴퓨터 화면에 창이 뜬다(SSE). 이 점포 주문만 보이고, 준비 완료(`READY_FOR_PICKUP`) 주문만 고를 수 있다.
4. 점주가 골라 [픽업 승인] → 확인 → 건마다 `PICKED_UP`. 지금 픽업 규칙(준비 완료·환불 `NONE`·기한 이내)과 [픽업 확인] 버튼은 그대로 둔다.

**정할 것:** 처음 체크 상태(비움 / 준비 완료 미리 체크), 카메라가 안 될 때 쓰는 6자리 코드를 넣을지, QR 유효 시간(제안 5분), QR 그리기 라이브러리 추가(frontend 공동 레포라 김진아·이태우 확인).

- [ ] order: 일회용 표 만들기(고객), 스캔 받기(점주 핸드폰), 점주 컴퓨터 SSE, 표로 미픽업 목록 보기, 여러 건 한 번에 승인 API. 표는 Valkey에만 두고 DB 표는 더하지 않는다.
- [ ] frontend: 고객 QR 화면(만료 전 저절로 새 QR), 점주 핸드폰 스캔 안내 화면, 점주 컴퓨터 확인·승인 창.
- [ ] order 추가 명세에 새 A 번호로 적는다.
- **완료 기준:** 고객 QR을 점주 핸드폰으로 찍으면 점주 컴퓨터에 그 고객의 이 점포 미픽업 주문이 뜨고, 고른 주문만 픽업 완료가 되며 고객 화면도 바뀐다.

### 마이페이지·회원정보 수정·비밀번호 변경 (11/4 멘토링)

**왜 하나:** 지금은 가입 뒤 내 정보를 보거나 바꿀 곳이 없다. 고객 메뉴 한 곳에서 내 정보·주문 내역·설정으로 간다.

- [ ] 마이페이지: 내 정보(이메일·이름·닉네임·지역, 이미 있는 `GET /members/me`)와 주문 내역·회원정보 수정·비밀번호 변경·회원탈퇴·공지·FAQ·이용약관·로그아웃으로 가는 메뉴.
- [ ] 회원정보 수정 (member 추가 명세 A3): 이름·닉네임·거주 시·도만 수정, 이메일은 수정 불가. 닉네임 중복 검사에서 본인 현재 값은 뺀다. 지난 주문은 주문 당시 이름을 유지한다. member API + 화면.
- [ ] 비밀번호 변경 (member 추가 명세 A4): 일반 가입 고객·점주·관리자. 현재·새 비밀번호·확인값, 가입 규칙과 같은 검사. Cognito를 쓰므로 gateway `/api/auth/*`에 길을 더한다. 구글 가입자에게는 메뉴를 숨긴다. 비밀번호는 DB·로그에 남기지 않는다.
- **정할 것:** 마이페이지를 점주도 쓰는지(명세의 수정·탈퇴는 고객만), 푸터 5개 메뉴에 '마이' 칸을 넣는지(푸터 담당과 맞춤), 비밀번호 재설정(잊었어요)도 같이 할지.
- **완료 기준:** 고객이 마이페이지에서 정보를 고치고 비밀번호를 바꾼 뒤 다시 로그인해도 바뀐 값이 유지된다.

### 회원탈퇴 (11/4 멘토링)

**흐름 (member 추가 명세 A6·A7):** 안내·최종 확인 → 진행 중 주문이 있으면 막는다(환불 처리 중·확인 중·실패도 진행 중) → Cognito 계정·프로필 삭제 → 탈퇴 이력(이메일 보관, 같은 이메일 재가입 가능) → 주문의 이름·닉네임을 '탈퇴 회원'으로.
