## 김진아

### prod 운영 자동화·알림 (11/2 추가)

prod가 실제 운영처럼 보이고, 문제가 생기면 디스코드로 바로 알게 한다. 대형 부하 테스트가 아니라 하루에 정해진 몇 번만 도는 작은 시나리오다([2차-사람별-할-일.md](2차-사람별-할-일.md) 맨 위 규칙의 "시뮬레이션"과 다르다).

1. 입고·주문·결제 시뮬레이터 prod 적용 (매일 자동 시나리오, 11/3 계획 정리)

**왜 하나:** prod를 남에게 보여 줄 때 점주 대시보드(주문 내역·매출·판매 순위), 고객 주문 내역, 알림 종이 비어 있으면 데모가 안 된다. 사람이 손으로 주문하지 않아도 prod를 켜 두면 하루 동안 입고 → 주문 → 결제 → 픽업 준비 → 픽업이 저절로 쌓이게 한다. dev는 개발용 시험 데이터만 두고, prod는 점포·고객·상품을 늘려 다양하고 풍부하게 만든다. 대형 부하 테스트가 아니다(하루 수십 건, 2차 문서 맨 위 규칙의 "시뮬레이션"과 다르다).

**정한 것 (11/3)**
- 토스 결제를 실제로 부르지 않는다. 시뮬레이터가 만든 주문만 order-service가 바로 "결제 완료"로 처리한다(아래 1-3, 경우님 확인 필요).
- 김진아-할일-목록 21(자동 입고)을 이 항목으로 넓힌다. 21은 여기로 옮긴다.

**전체 흐름 (하루)**

| 시각(KST, 평일) | 시뮬레이터가 하는 일 | 화면에 생기는 것 |
| --- | --- | --- |
| 켜질 때 1번 + 09:20 | 점포마다 오늘 입고(INBOUND). `shipmentId`를 `SHP-<날짜>-AM-S<점포>`로 고정해서 같은 날 두 번 보내도 inventory가 한 번만 받는다 | 고객 상품 목록·점주 재고, 유통기한 임박·경과 알림(inventory 크론) |

| 결제 5–20분 뒤 | 점주 대신 픽업 준비 완료(`POST /owner/orders/{id}/ready`) | 고객 "픽업 준비 완료" 알림 |

| 20:30 | 그날 시나리오 끝 (21:00 prod 끄기 전) | |

**1-1. prod 데이터 늘리기 (infra 시드, 김진아, 먼저 한다)**

시뮬레이터는 여기서 만든 점포·고객으로 돈다. 데모는 서울만 보여 주므로 서울 기준 점포 10곳으로 한다.

- [ ] 점포: prod를 3곳 → 10곳으로 늘린다(서울 여러 구에 고르게, 비로그인 기본 지역이 서울이라 모두 SEOUL). `scripts/seed/prod-member.sql`에 ID 4–10과 이름·주소를 추가한다. 점포는 점주가 이어져야 ACTIVE가 되므로 점주 계정도 7개 더 만든다(`seed-cognito.ps1 -Env prod`, 이메일 형식은 지금 prod와 같은 `<지점 영문>@freshlink.co.kr`).
- [ ] 가상 고객: prod Cognito에 40명 정도를 만든다(dev는 지금처럼 몇 명만). 한국 이름, 이메일·이름 어디에도 "test"를 넣지 않는다. `AdminCreateUser`를 메일 안 보내기(`MessageAction SUPPRESS`)로, `email_verified=true`, 그룹 `CUSTOMER`, 영구 비밀번호. 가입 Lambda가 돌지 않으므로 member 행(role CUSTOMER)도 시드 SQL로 넣는다. 고객마다 단골 점포 1–2곳을 정해 둔다(10곳에 고르게 나눠 점포마다 단골이 4명 이상).
- [ ] 자격: 비밀번호는 Secrets Manager `freshlink-prod-seed-accounts`에 지금처럼 같이 둔다(사람이 데모 때 고객으로 로그인할 수 있게). 시뮬레이터에는 비밀번호가 필요 없고 고객 sub·단골 점포만 필요하다 → 비밀 `freshlink-prod/simulator/customers`(JSON) → External Secrets → 환경 변수. dev도 같은 모양 `freshlink-dev/simulator/customers`.
- [ ] 시뮬레이터 IRSA는 SQS 보내기만 있으면 된다(Secrets Manager는 ESO가 읽는다). ESO가 새 비밀을 읽을 수 있는지 정책을 확인한다.

**1-2. 시뮬레이터 코드 (logistics-simulator, 김진아)**
- [ ] `@Scheduled` + 설정값 `simulator.schedule.*`로 위 흐름을 1-1의 점포 10곳·고객으로 돈다. 파드 1개라 ShedLock은 쓰지 않는다. DB가 없으므로 진행 중인 주문은 메모리에만 둔다(파드가 다시 뜨면 그날 남은 픽업 처리만 빠진다. 입고는 고정 `shipmentId`라 다시 보내도 된다).
- [ ] 유통기한을 고정 날짜(지금 preset 10/09·10/20) 대신 "오늘 + N일"로 계산한다. 분류별 기본값: 도시락·김밥·샌드위치·샐러드 0–1일, 유제품·디저트 3–10일, 빵 2–4일, 과일·신선식품 3–7일, 음료 30–90일, 라면·즉석식품 90–180일. 점포마다 1–2개 lot은 오늘 마감(임박 알림), 1개는 어제 마감(경과 알림·폐기 화면)으로 넣는다.
- [ ] 입고량: 점포마다 30개 상품 중 20–30개를 고르고 수량 5–30개. 점포별로 seed(점포 ID + 날짜)를 고정한 난수라 같은 날 다시 돌려도 같은 값이 나온다.
- [ ] 주문: 고객 1명이 단골 점포 1–2곳에서 상품 1개·수량 1–3개(order API 최대 5). 재고는 inventory `GET /stores/{storeId}/products`(클러스터 안 `http://inventory-service:8080`)로 판매 중인 것만 고른다. 선착순 상품은 고르지 않는다.
- [ ] 주문 순서: `POST /orders`(헤더 `Idempotency-Key` UUID, `X-User-Id` = 고객 sub, `X-User-Role: CUSTOMER`) → `GET /orders/{id}`를 2초마다 최대 30초 봐서 `PAYMENT_WAITING`이 되면 → 결제 완료 API(1-3). 재고 부족(`OUT_OF_STOCK`)이면 그냥 넘어간다(실제로도 생기는 일이라 그대로 둔다).
- [ ] 다양하게: 하루 주문의 약 5%는 결제하지 않고 두어 10분 뒤 `EXPIRED`가 되게, 약 3%는 결제 후 고객 취소·환불(1-3의 환불 처리가 된 뒤에만 켠다). (선택) 선착순 상품을 하루 한 번 열어 고객 몇 명이 대기열을 거쳐 사게 한다(경우님 대기열 API를 그대로 쓴다. 태우님 재고 한도).
- [ ] order·inventory는 gateway를 거치지 않고 클러스터 안 Service 이름으로 부른다(gateway가 넣는 `X-User-*` 헤더를 시뮬레이터가 직접 넣는다. 지금 서비스끼리 부르는 방식과 같다). 실패하면 로그만 남기고 다음 주문으로 넘어간다.
- [ ] 지금 있는 `POST /simulator/shipments`(손 입고)는 그대로 둔다. 상태를 볼 `GET /simulator/schedule`(오늘 입고 여부, 오늘 주문 수, 다음 실행 시각)을 추가한다.
- [ ] 테스트: 시계를 고정한 단위 테스트(유통기한 계산, 고정 `shipmentId`, 시간대별 주문 수), order·inventory는 가짜 서버(MockRestServiceServer). 실제 큐·실제 API는 부르지 않는다.

**설정값 예시 (`simulator.schedule.*`)**

| 키 | 뜻 | dev | prod |
| --- | --- | --- | --- |
| `enabled` | 스케줄 전체 켜기 | `true` | `true` |
| `inbound-cron` | 아침 입고 시각 | `0 20 9 * * MON-FRI` | `0 20 9 * * MON-FRI` |
| `inbound-on-startup` | 켜질 때 오늘 입고 한 번 | `true` | `true` |
| `orders.enabled` | 주문 시나리오 켜기 | `false` (팀원 시험 데이터와 섞이지 않게. 필요할 때만 켬) | `true` |
| `orders.per-store-per-day` | 점포당 하루 주문 수 | 2–3 | 5–15 (10곳이면 하루 50–150건) |
| `orders.window` | 주문 시간 | 10:00–20:00 | 10:00–20:00 |
| `pickup.ready-after` / `pickup.done-after` | 준비·픽업까지 걸리는 시간 | 5–20분 / 10–40분 | 같음 |
| `pickup.no-show-rate` | 픽업 안 하는 비율 | 0.1 | 0.1 |
| `stores` | 대상 점포 ID (1-1에서 만든 점포) | 1–3 | 1–10 |

**1-3. order-service: 시뮬레이터 주문 결제 완료 (경우님께 묻기)**
- [ ] 경우님께 아래를 묻고 누가 만들지 정한다(order는 경우님 레포).
  - 결제 완료 API를 하나 둔다. 예: `POST /ops/orders/{id}/simulated-payment`. `/ops/**`라 gateway 라우트가 없어 밖에서 못 부른다(OP-01·OP-02와 같다). 설정 `app.simulated-payment.enabled`(기본 `false`, 시뮬레이터가 도는 환경만 `true`)일 때만 열린다.
  - 하는 일: `PAYMENT_WAITING`이고 결제 기한·픽업 기한 안인 주문만 → `Payment`를 승인 완료로 저장(`payment_key`는 `SIM-<UUID>`처럼 토스 키와 구분, 결제 수단은 화면에 자연스러운 값) → 지금 쓰는 `PaymentResultWriter.paid()`를 그대로 불러 `PAID` + CONFIRM + 점주 새 주문 알림 + 매출 SSE. 토스는 부르지 않는다.
  - 시뮬레이터 주문을 고객·점주가 화면에서 취소하면 지금 환불 로직이 토스 취소를 불러 실패한다. `SIM-` 결제는 토스를 건너뛰고 바로 환불 완료로 처리할 수 있는지(아니면 시뮬레이터 주문은 취소 버튼을 막을지).
  - 그 밖에 order 쪽에 필요한 것(결제 자동 확인 스케줄러가 `SIM-` 결제를 건드리지 않는지, 매출 대시보드 집계가 `payment` 표를 같이 보는지).
- [ ] 확인할 것(태우님): 유통기한이 이미 지난 lot을 INBOUND로 넣어도 되는지(지금 preset이 그렇게 넣고 있다), 유통기한 임박 알림 기준(며칠 전부터인지), prod `EXPIRY_CRON`이 매시라 아침 입고 뒤 1시간 안에 알림이 뜨는지.

**1-4. gitops·켜고 끄기 (김진아)**
- [ ] `envs/dev|prod/logistics-simulator/values.yaml`에 위 `simulator.schedule.*` 값을 환경 변수로 넣고, 고객 비밀을 External Secret으로 붙인다.
- [ ] prod 켜고 끄기 일정을 정한다(사용자 결정). 지금 prod는 필요할 때만 손으로 켜고 매일 21:05에 자동으로 지운다. 시나리오가 매일 쌓이려면 (A) 평일 09:00 자동 생성 일정을 추가하거나(비용 증가, 50만 원 예산 안인지 계산), (B) 지금처럼 필요한 날만 켜고 켜진 날에만 쌓는다. B라도 "켜질 때 오늘 입고"가 있어 켜자마자 데모가 된다. (11/3 사용자 제안) (C) 개발이 끝났으니 dev는 평소 꺼 두고 추가 기능 개발·QA 때만 켜고, 그 대신 prod를 평일 09:00–21:00 자동으로 켠다. 이러면 dev 비용이 빠져 A의 늘어난 비용을 메운다. 정하면 infra 스케줄(dev 노드 그룹·NAT·RDS 켜기 끄기, prod 생성 일정)을 바꾸는 PR을 따로 만든다.
- [ ] (제안, 사용자 결정) 첫날부터 대시보드가 비지 않게 지난 30일 주문·결제 기록을 **한 번만** 채우고, 그 뒤로는 매일 시나리오로 쌓는다. 방법은 둘 중 하나: 시뮬레이터에 날짜를 받는 1회용 API를 두거나, order `orders`·`payment` 표에 직접 넣는 SQL(`paid_at`을 과거로). 매출·주문 내역·판매 순위만 채우고 재고 lot은 건드리지 않는다. 판매 순위가 inventory 기록을 보면 태우님과 같이 본다. 경우님 표 구조라 같이 정한다.

**1-5. 순서**
0. (C로 정하면) 켜고 끄기 일정을 dev → prod로 옮긴다: 평일 09:00–21:00 EventBridge 일정(RDS·nano)과 Actions 일정(NAT·노드 그룹·클러스터 생성·삭제)을 prod에 걸고, dev는 손으로 만들고 지우기만 남긴다(추가 기능 개발·QA 때만). 바꾸기 전에 태우님·경우님께 먼저 알린다. infra PR + global·persistent apply는 김진아가 한다.
1. 경우님 답(1-3) → order PR(dev) → dev에서 시뮬레이터 없이 결제 완료 API를 port-forward로 한 번 불러 확인
2. 시뮬레이터 PR(dev) → dev에서 `orders.enabled=true`를 잠깐 켜고 한 시간 돌려 본다(주문·알림·매출 확인 뒤 다시 `false`)
3. infra 시드 PR(1-1, 점포 10곳·고객 40명) → prod 켜는 날 `seed-cognito.ps1 -Env prod`·`seed-db.ps1 -Env prod`
4. 다음 prod 릴리스 때 order·simulator를 main으로, gitops prod 값 PR
5. prod를 하루 켜 두고 저녁에 점주 대시보드·고객 주문 내역·알림을 확인

- **완료 기준:** prod를 켜 두면 손대지 않아도 하루 동안 서울 10개 점포에 입고·주문·결제·픽업·매출·알림(새 주문, 픽업 준비 완료, 유통기한 임박·경과)이 쌓이고, 점주 대시보드와 고객 주문 내역에 그날 기록이 보인다. 어디에도 "test"가 보이지 않는다.

2. 디스코드 알림 (ArgoCD 실패, AWS·인프라 오류)
- [ ] ArgoCD Notifications로 동기화 실패·Health Degraded·Missing을 디스코드로 보낸다(dev·prod, 메시지에 환경·앱 이름·리비전·ArgoCD 링크). 웹훅 주소는 gitops(공개 레포)에 적지 않고 Secrets Manager → External Secrets로 `argocd-notifications-secret`에 넣는다. 2차 문서 김진아 "배포 알림 웹훅"의 (선택) 항목을 이것으로 실제로 한다.
