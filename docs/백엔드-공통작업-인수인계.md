## 1. 공통 기준 (팀 전체)

FreshLink 백엔드 레포는 모두 이 기준으로 만듭니다. 바꿔야 할 일이 생기면 김진아에게 먼저 알려 주세요.

### 1-1. 버전

| 항목 | 기준 | 이유 |
|---|---|---|
| Java | **21** (LTS) | 모든 레포 동일 |
| Spring Boot | **4.0.x** | 3.4·3.5는 무료 지원이 끝났다(3.5는 2026-06-30 종료). 4.0은 프로젝트가 끝날 때까지 지원된다 |
| Spring Cloud | **2025.1.x** (Oakwood) | Boot 4.0과 짝인 버전. gateway에서 쓴다 |
| Spring Cloud AWS | **4.x** 중 Boot 4.0과 호환되는 최신 | SQS 송수신. 뼈대를 만들 때 공식 호환표로 확인한다 |
| JSON | **Jackson 3** (Boot 4 기본) | common의 DTO도 Jackson 3 기준으로 만든다 |
| 빌드 | Gradle Wrapper(9.x), Groovy `build.gradle` | `./gradlew`만 쓴다 |

- 정확한 패치 버전은 작업 A를 만들 때 정하고, **네 레포와 common이 같은 Boot 버전**을 씁니다. 정한 버전은 PR 설명에 적습니다.
- `group = 'com.freshlink'`, 패키지는 `com.freshlink.<서비스>` (예: `com.freshlink.inventory`, `com.freshlink.common`).

### 1-2. 환경과 프로필

- 환경은 **AWS dev**와 **AWS prod** 두 개입니다. 개발도 dev 환경(dev RDS·dev SQS·dev Cognito)에 붙어서 합니다.
- Spring 프로필은 **`dev`, `prod` 두 개만** 둡니다.
- `application-dev.yml`과 `application-prod.yml`은 **키가 같고, 값은 모두 환경 변수**로 받습니다. 코드나 설정 파일에 주소·비밀번호를 적지 않습니다.

| 환경 변수 | 용도 |
|---|---|
| `SPRING_PROFILES_ACTIVE` | `dev` 또는 `prod` |
| `DB_URL`, `DB_USERNAME`, `DB_PASSWORD` | 서비스별 DB |
| `QUEUE_PREFIX` | 큐 이름 앞부분. 예: `dev-`, 개인 시험은 `dev-taewoo-` |
| `COGNITO_ISSUER_URI`, `COGNITO_CLIENT_ID` | gateway 토큰 검증 |

### 1-3. 이름 규칙

- AWS 리소스: `freshlink-<env>-<이름>` (예: `freshlink-dev-mysql`).
- 큐: `<env>-inventory-commands.fifo`, `<env>-inventory-results`. 서비스는 큐 이름을 코드에 넣지 않고 설정 값 `app.queue.commands`, `app.queue.results`로 받습니다.

### 1-4. 포트와 관측

- **포트는 8080 하나입니다.** 서버와 Actuator가 같은 포트를 쓰고, 관리 포트는 따로 두지 않습니다.
- Actuator는 `health`, `prometheus`를 엽니다.
- 시간대는 `Asia/Seoul`입니다. 시각은 ISO-8601 `+09:00`으로 주고받습니다.

### 1-5. 브랜치와 배포

- `dev` 브랜치에 합치면 dev 환경에 자동 배포됩니다.
- `main`에 합치면 dev에서 검증한 **같은 이미지**가 prod로 올라갑니다(다시 빌드하지 않음).
- 레포마다 담당자가 있습니다. 담당자가 아닌 사람은 `dev` 대상 PR로 올리고, 담당자가 합칩니다.

## 3. 작업 B. common v0.1.0

### 3-1. 왜 필요한가

inventory-service, order-service, logistics-simulator가 SQS로 쪽지를 주고받습니다. 쪽지 클래스를 각자 만들면 필드가 어긋나서 서로 못 읽습니다. 그래서 common에 한 번만 만들고, 세 서비스가 같은 버전(`com.freshlink:common:0.1.0`)을 가져다 씁니다.

### 3-2. 범위

| 이번에 한다 | 이번에 안 한다 |
|---|---|
| Gradle 라이브러리 설정 (`java-library`, `maven-publish`) | Outbox 표·발행기, 멱등 처리 (v0.2.0, 김진아) |
| `v*` 태그 → GitHub Packages 배포 워크플로 | 큐 이름 상수 (1-3처럼 설정 값으로 받음) |
| 쪽지 공통 부모 + DTO 7종 + enum | SQS 보내기·받기 코드, Spring 자동 설정 |
| FIFO 그룹 ID·중복 제거 ID 규칙 | 서비스별 오류 코드 목록 (각 서비스 레포에서 enum으로) |
| 공통 오류 응답 `ErrorResponse` | |
| JSON 변환 테스트 | |

### 3-3. 이미 정해진 쪽지 형식 (이태우님과 협의 완료)

**모든 쪽지의 공통 필드**

| 필드 | 타입 | 규칙 |
|---|---|---|
| `messageId` | String (UUID) | 쪽지마다 새로 만든다. 받는 쪽은 이 값으로 중복을 거른다 |
| `type` | String | 아래 8개 중 하나 (v0.5.0에서 `RETURN` 추가) |
| `createdAt` | ISO-8601 `+09:00` | 예: `2026-10-15T12:30:00+09:00` |

**타입별 필드**

| type | 보내는 곳 | 받는 큐 | 필드 |
|---|---|---|---|
| `INBOUND` | logistics-simulator | inventory-commands.fifo | `storeId`, `shipmentId`, `items[{productCode, quantity, expiryDate}]` |
| `RESERVE` | order-service | inventory-commands.fifo | `orderId`, `storeId`, `productId`, `quantity` |
| `CONFIRM` | order-service | inventory-commands.fifo | `orderId`, `storeId` |
| `RELEASE` | order-service | inventory-commands.fifo | `orderId`, `storeId`, `reason`(`PAYMENT_FAILED`·`EXPIRED`·`CANCELED`) |
| `RETURN` | order-service | inventory-commands.fifo | `orderId`, `storeId` |
| `DISPOSE` | inventory-service | inventory-commands.fifo | `disposalId`, `storeId`, `lotId`, `quantity`, `requestedBy` |
| `RESERVED` | inventory-service | inventory-results | `orderId`, `storeId`, `productId`, `productName`, `quantity`, `unitPrice`, `lots[{lotId, quantity, expiryDate}]` |
| `RESERVE_FAILED` | inventory-service | inventory-results | `orderId`, `storeId`, `productId`, `reason`(`OUT_OF_STOCK`·`PRODUCT_NOT_FOUND`·`INVALID_QUANTITY`), `availableQuantity` |

**v0.5.0에서 더한 것 (10/30, 김진아·이태우 합의)**
- `RELEASE` 사유 `CANCELED`: 결제 전 고객 취소(order A7). 새 쪽지 없이 예약만 푼다. order는 결제 승인 중(`PAYMENT_APPROVING`)에는 취소를 받지 않는다(취소 뒤 CONFIRM이 오는 일이 없게).
- `RETURN`: 환불(A9) 뒤 확정된 판매 재고를 되돌린다(order A10). order는 `orderId`·`storeId`만 보내고, inventory가 그 주문의 판매 기록(SALE, `refId = orderId`)으로 원래 lot과 수량을 찾는다. 같은 주문의 RETURN이 다시 와도(`messageId`가 달라도) 한 번만 반영한다.
- 배포 순서: common v0.5.0 → inventory가 올려서 배포 → 그다음 order가 보내기 시작한다. 옛 common을 쓰는 inventory는 `CANCELED`·`RETURN`을 읽지 못해 실패하고 3번 뒤 DLQ로 간다.
- (추천, 확정 전) RETURN으로 다시 생긴 재고는 재입고 알림을 보내지 않고 INBOUND만 재입고로 본다.
- 원래 lot의 유통기한이 이미 지났을 때 복원할지 폐기로 기록할지는 inventory(이태우)와 김진아가 정한다(10/30 두 의견이 다름).

**그 밖의 규칙**
- `storeId`는 **숫자**(`Long`)입니다. `"S001"` 같은 코드 문자열은 쓰지 않습니다.
- FIFO 큐의 메시지 그룹 ID는 `storeId`를 문자열로 바꾼 값(`"1"`), 중복 제거 ID는 `messageId`입니다. 점포 안에서는 순서가 지켜지고, 점포끼리는 병렬로 처리됩니다.
- 유통기한에 날짜만 오면(`2026-10-20`) 그날 23:59:59 한국 시간으로 해석합니다.
- 오류 응답은 `{"code": "LOT_NOT_IN_STORE", "message": "다른 점포의 lot입니다", "traceId": "..."}`입니다. `traceId`(Zipkin 추적 ID)는 항상 넣습니다.

**타입이 안 정해졌던 필드 (김진아가 정한 기본값, 다르게 하고 싶으면 PR에서 말해 주세요)**

| 필드 | 타입 |
|---|---|
| `orderId`, `productId`, `lotId`, `disposalId` | `Long` (DB BIGINT id) |
| `shipmentId`, `productCode`, `productName` | `String` |
| `quantity`, `availableQuantity` | `int` |
| `unitPrice` | `long` (원 단위) |
| `requestedBy` | `String` (점주의 Cognito sub, UUID 문자열) |
| `expiryDate`, `createdAt` | `OffsetDateTime` |

### 3-4. 클래스 구성

```
com.freshlink.common
├── message/
│   ├── MessageType            # enum 8개
│   ├── BaseMessage            # messageId, type, createdAt + 다형성 설정
│   ├── StoreScoped            # storeId(), messageGroupId()
│   ├── InboundMessage, ReserveMessage, ConfirmMessage, ReleaseMessage,
│   ├── ReturnMessage, DisposeMessage, ReservedMessage, ReserveFailedMessage
│   ├── InboundItem, ReservedLot
│   ├── ReleaseReason, ReserveFailReason
│   ├── MessageJson            # 한국 시간·ISO-8601로 설정된 JSON 변환기 도우미
│   └── ExpiryDateDeserializer # "2026-10-20" → 2026-10-20T23:59:59+09:00
└── error/
    └── ErrorResponse          # record(code, message, traceId)
```

- DTO는 Java `record`로 만듭니다.
- `type` 값으로 클래스를 고르게 합니다(`@JsonTypeInfo` + `@JsonSubTypes` 8개). 받는 쪽은 `BaseMessage`로 읽기만 하면 알맞은 클래스가 나옵니다.
- 새 쪽지는 팩토리로 만듭니다. 예: `ReserveMessage.of(orderId, storeId, productId, quantity)`가 `messageId`와 `createdAt`을 채웁니다.
- 8종 모두 `storeId`가 있으므로 `StoreScoped`를 구현합니다. `messageGroupId()`는 `String.valueOf(storeId())`입니다.
- 모르는 필드가 와도 실패하지 않게 합니다. 나중에 필드를 추가해도 옛 버전이 쪽지를 읽을 수 있습니다.
- Spring 의존성은 넣지 않습니다. Jackson 3(1-1)만 `api`로 둡니다.

예시 (RESERVE):

```json
{
  "messageId": "b3f1c2e0-7a1d-4c55-9e0a-1f2a3b4c5d6e",
  "type": "RESERVE",
  "createdAt": "2026-10-15T12:30:00+09:00",
  "orderId": 1024,
  "storeId": 1,
  "productId": 15,
  "quantity": 1
}
```

### 3-5. 빌드와 배포

- `build.gradle`: `java-library`, `maven-publish`. 실행 jar를 만들지 않습니다. 버전은 Boot 4.0 BOM으로 맞춥니다.
- 버전은 태그에서 받고, 태그 빌드가 아니면 `0.1.0-SNAPSHOT`입니다.
- 배포 저장소: `https://maven.pkg.github.com/sesac-freshlink/common`
- `.github/workflows/publish.yml`: `v*` 태그 push → Java 21 → `./gradlew test` → `./gradlew publish`. 권한은 `contents: read`, `packages: write`. `GITHUB_TOKEN`만 씁니다.
- README에 서비스에서 가져다 쓰는 방법(GitHub Packages 저장소 설정, `implementation 'com.freshlink:common:0.1.0'`, `read:packages` 토큰 필요)을 적습니다.

### 3-6. 테스트

- 7종 각각: 객체 → JSON → `BaseMessage`로 읽기 → 같은 클래스·같은 값.
- 3-4의 RESERVE 예시 JSON을 그대로 읽으면 `ReserveMessage`가 나온다.
- `expiryDate`가 `"2026-10-20"`이면 `2026-10-20T23:59:59+09:00`, 일시가 오면 그대로.
- 모르는 필드가 섞인 JSON도 읽힌다.
- `messageGroupId()`가 `"1"`이다.
- `ErrorResponse`가 `code`, `message`, `traceId` 세 키로 나간다.

### 3-7. 완료 기준

- `./gradlew build`가 통과하고, 3-6 테스트가 모두 있습니다.
- `v0.1.0`이 GitHub Packages에 있습니다.
- 다른 서비스에서 `implementation 'com.freshlink:common:0.1.0'`을 넣으면 `ReserveMessage`, `ErrorResponse`가 import됩니다.
